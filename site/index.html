The problem

Construction progress is still tracked by people walking the site with a clipboard. At the Afcons casting yard, supervisors maintain a handwritten time sheet recording the start time, end time and duration of every process for each mould. It works, but it is slow, subjective, and impossible to scale: a supervisor can only watch so many moulds at once, and the record arrives hours after the fact.

Precast manufacturing is unusually well suited to automation. The workflow is cyclical and predictable, the workspace is constrained, and the same six stages repeat for every segment. That makes progress monitoring a tractable stage-classification problem rather than an open-ended scene-understanding one.

What we built

A single pipeline that reads a video and outputs three things a project manager can act on: a digital time-cycle sheet, a Lean productivity breakdown per mould, and a safety event log — all exportable, including as a Primavera P6 XER file.

Three monitoring pillars

Pillar 01

Progress & time-cycle

A YOLO11m model classifies which of six production stages each mould is in, frame by frame. A dedicated mould detector locates all three moulds and assigns each detected activity to the right one by centroid containment, so overlapping work on adjacent moulds is never conflated.

Timestamps are read straight off the video by OCR, so confirmed stage transitions become a real digital time sheet — start, end and duration per stage, per mould, with no manual entry.

  • Six-stage classification
  • OCR-derived real timestamps
  • CSV and Primavera P6 XER export

Pillar 02

Worker productivity

Instead of classifying individual worker behaviour, the system analyses zones. An instance-segmentation model carves out an exclusive zone around each mould, workers are detected and tracked with ByteTrack, and their activity is read jointly with the production phase happening at their location.

Body motion alone misses fine manual work such as trowelling, so a pose model adds wrist-level movement detection — a worker standing still with moving hands is counted as active, not idle.

  • Exclusive mould zones, no double-counting
  • Pose-based wrist activity detection
  • Lean VA / NVAN / NVA classification

Pillar 03

Safety monitoring

The same worker detections feed a safety layer that watches for PPE compliance and dangerous proximity between workers and active machinery — most critically the vacuum lifter as it moves a finished segment.

Events are logged with timestamps and the frames that triggered them, so an incident can be reviewed rather than just counted.

  • PPE violation detection
  • Proximity and danger-zone alerts
  • Event log with captured frames

How a frame becomes a metric

  1. 1

    Operator sets the region of interest

    A boundary polyline is drawn once on the first frame, separating the working area from background. Workers whose feet fall above the interpolated line are excluded, handling perspective without a fixed threshold.

  2. 2

    Mould zones are computed once

    Frames from the first 10% of the video are sampled until at least two moulds are detected. Masks are dilated with an asymmetric 301×151 kernel to capture nearby workers, then overlaps are removed so every zone is exclusive.

  3. 3

    Detection, tracking and filtering

    Workers are detected and tracked across frames with ByteTrack, then passed through size checks, static-artifact rejection, ghost-worker memory for brief occlusions, and geometric deduplication.

  4. 4

    Temporal smoothing

    Raw per-frame predictions are noisy. A class is only confirmed once it appears in at least 3 of the last 10 processed frames — which removed most false transitions without retraining anything.

  5. 5

    Labour gating and Lean classification

    A phase is only recorded as productive if enough active workers are actually present. Machine-driven phases bypass this. Each state maps to a Lean category and aggregates into crew balance charts.

Model performance

The first model was trained on a public 546-image dataset and scored well on its own split — but collapsed on real footage from the yard. Grooves on the mould surface were read as rebar; simultaneous pours went undetected. Closing that domain gap meant recording our own data on site.

Rebar cage placement is the weakest class, which matches what it looks like on site: the cage is often half-inserted or hidden behind workers, so the transitional frames are genuinely ambiguous.

Mould segmentation

A YOLOv8n-seg model was trained in three stages across three camera sources to produce the spatially stable mould masks that anchor the whole zone-based analysis. On the combined 3,615-image validation set it reaches a mask mAP50-95 of 0.995 — the masks hug the true mould boundary rather than merely covering the region, which is what the zone-exclusivity computation downstream depends on.

Building the dataset

A Brinno BCC300 timelapse camera was installed at the yard, covering three adjacent moulds across full production cycles. Footage was annotated in CVAT, yielding 67,920 frames. Curing dominated the raw data at 71,626 instances against just 54 for rebar cage placement, so over-represented classes were subsampled and under-represented ones augmented with Albumentations.

See it run on real footage

The dashboard streams video in place rather than downloading it — the host serves byte ranges and the camera writes the MP4 index at the front of the file, so the pipeline reads frames straight off the network. That matters here: timelapse footage has no temporal redundancy for the encoder to exploit, so a 7-minute clip runs to 4.2 GB. Point it at a video on Hugging Face (recommended — no download quota) or paste a public Google Drive link.

Queue a batch

Add several videos to the analysis queue, choose which of the three analyses each one should run, reorder them, and let the whole batch process back-to-back without supervision.

Keep every result

Each finished run is archived separately — raw JSON, a spreadsheet-ready CSV, and any generated imagery — so a new run never overwrites an old one. Download a single run or the entire history as a ZIP.

git clone https://github.com/god-Krico/IDP.git

Model weights download automatically on first launch. A GPU is strongly recommended — four models run per frame, so CPU-only inference on a long video is slow.

What went wrong, and what fixed it

The public dataset didn't survive contact with the site.
A model at 0.994 mAP50 on its own validation split failed on real CCTV footage — mould grooves misread as rebar, low-confidence pours, empty and freshly filled moulds indistinguishable under shed lighting. We recorded and annotated our own site data and retrained.
Curing swamped everything else.
Curing is the longest stage, so it contributed 71,626 of the annotated instances against 54 for rebar cage placement. Trained as-is, the model becomes a curing detector. Targeted subsampling plus class-specific augmentation, anchored to the concrete pouring count, rebalanced it.
Single-frame noise created phantom stage transitions.
Passing workers and the vacuum lifter caused momentary misclassifications that were logged as real transitions. The 3-of-10 sliding window persistence filter eliminated them with no retraining and no meaningful added latency.
Still workers with moving hands were counted as idle.
Pixel-difference motion detection misses fine manual work such as trowelling. Adding a pose model and tracking wrist displacement lets the system label these workers Active-Hands instead of idle.
